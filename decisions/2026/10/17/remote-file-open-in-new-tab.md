# Remote file preview: open in a new tab via token-only capability links

## Context
The desktop file preview offers "Open in default app", which runs on the host. In browser/remote mode the host is WSL or a remote box, so the button was hidden and the only way to read a file was the in-app preview. Users want the file in their own browser tab (HTML reports, Markdown rendered by their own extension) or downloaded to their device. The artifact viewer's and image/video viewer's open buttons had the same gap.

## Investigation
Agent-written HTML served from the dev3 origin would run with the signed-in user's authority (RPC, terminals). `Content-Security-Policy: sandbox` without `allow-same-origin` gives the page an opaque origin, but an opaque origin never sends the `SameSite=Strict` session cookie, so a page's own CSS and images cannot authenticate by cookie. A Markdown extension that renders raw HTML can inject script into any text document, so sandboxing only HTML is not enough.

## Decision
- `createFileLink` (`src/bun/rpc-handlers/terminal-paths.ts`) gates the path like `readFilePreview`, then mints a fresh 24-byte token per click (`src/bun/file-links.ts`, 12 h TTL, 256 cap evicting the least recently used). Only a page (HTML/SVG) whose real folder is strictly inside a task worktree or project checkout (nearest `.git` above it), not inside a dot-folder of it, not reached through a symlink into another checkout, and not in dev3's own storage, gets its folder; files that checkout's `.gitignore` excludes (local secrets) are refused under it, except files ignored by the very rule that ignores the page (its build-output siblings). `git check-ignore -v -n` decides; any failure refuses; verdicts are cached per link and at most 4 checks run at once. Everything else is one file. `createFileLink` mints only the link asked for; a download link is single-file with a 60 s TTL.
- The scope is pinned to real paths at mint time. Each URL segment must be one plain name (no `%2F`, `.`/`..`, empty, NUL; no `\` or `:` on Windows), the target must be inside the root as a string before any filesystem call, and its real path (`realpathSync.native`, which expands 8.3 names) must stay inside with no dot-file/folder other than the entry.
- `/file/<token>/<rel>` (`remote-access-server.ts`) is token-only, like `/p/`. Every response, errors included, has `nosniff` and `no-store`. Markdown is shown inline by Firefox ≥ 128 (bug 1319262) and Chromium. Everything rendered carries a CSP sandbox allowing only scripts and sandboxed popups (no same-origin, forms, modals, downloads or sandbox escape), except video and audio, whose media document runs no page script and refuses a sandbox. PDFs are only ever sent as attachments: a PDF viewer cannot run sandboxed. Markdown goes out raw as `text/markdown`, sandboxed. `?download=1` forces an attachment. Types live in `src/shared/file-link-types.ts`, shared with the renderer.
- The artifact viewer's remote "Open in browser" (`createArtifactLink`, `sharedArtifactLinkScope`) and the image/video viewer, lightbox and attachment card go through the same links, replacing a `blob:` URL that ran with the dev3 origin's authority and lost relative assets.
- "Open on Windows" (`src/bun/wsl-host.ts`) runs, with a 15 s timeout, `Invoke-Item -LiteralPath` in PowerShell with the path in a WSLENV `/p` variable (explorer.exe splits arguments at commas), only for document/media types (`WINDOWS_OPEN_SAFE_EXTS`: the default verb runs scripts; CSV and PDF excluded for Excel formulas and PDF script) and never for a path with `:`; both the name and its real target must pass. `sw.js` never takes over a `/file/` tab on a notification click. The server needs WSL interop; the loopback-hostname check is renderer-side only, a UX gate (`src/mainview/file-open-browser.ts`).

## Risks
- The URL is the credential for 12 h, and a page can read its own URL: anything the page leaks reaches whatever the token covers — its own folder at most, never a checkout root or dot-files.
- No CORS headers are sent, so module scripts, web fonts and `fetch()` of siblings do not load in a report opened this way; a page cannot reach `../` assets above its own folder either.
- Each request opens the file once (non-blocking, so a planted FIFO cannot hang it) and serves only from that handle, after checking the opened file is the checked one (`/proc/self/fd` on Linux; device/inode plus a fresh realpath elsewhere, which leaves a narrow race on macOS/Windows). `createFileLink` resolves the file once and pins that same real path.
- Files up to 1 MB, and every 206 (at most 1 MB), are sent from memory: Bun sends any stream body chunked and WebKit rejects a chunked 206. Only larger files stream; at most 64 (16 per token) at once, a further one waits up to 10 s for a slot rather than being refused, so a page's burst of assets always loads. A slot is released when the body ends, is cancelled, or the request's signal aborts (also when it aborted before the listener existed) — Bun never cancels the body of a client that left before reading it. A token holder with many stalled sockets can still pin about 1 MB each. A Bun FileHandle closed during a pending read leaks its descriptor, so `fileRangeStream` closes only after the read settles, which also fixes the session-only `/shared-video/` route sharing the function (it now passes its request signal too). `bun run test:file-links-e2e` checks these over a real socket.
- A scripted page shown on the user's own dev3 hostname can still draw a fake access-code prompt; the sandbox does not prevent that. Serving `/file/` from a separate origin would.
- Links are not tied to a session: they outlive sign-out until expiry or a server restart.
- "Open on Windows" hands HTML/SVG to the Windows default browser unsandboxed, as the desktop's "Open in default app" does.
- "Same PC" is inferred from a loopback hostname: an SSH or VS Code port-forward to `localhost` also passes, and "Open on Windows" then opens on the forwarding host.

## Alternatives considered
Session-cookie auth on the route: breaks every subresource of a sandboxed page. Rendering Markdown to HTML on the server: rejected so users keep their own renderer. Serving HTML unsandboxed: gives an agent's page the user's dev3 session. One reusable token per folder: a leaked link would live as long as the user kept opening files there.
