# Opting a routed model into its million-token window

## Context

Claude Code assumes a 200k context window unless the model string it selects carries `[1m]`, and that number is the auto-compact threshold. Every model in the recommended set publishes a far larger window (Qwen3.8 Max 1 000 000; GLM 5.2, Kimi K3 and DeepSeek V4 Flash 1 048 576 through their top provider), so a routed session was compacting roughly five times earlier than the provider required. The same question raised a second one: what actually happens to reasoning effort on the way out.

## Investigation

Both were measured on the wire rather than argued from docs, with a local sink logging request bodies and a 400 back.

**The suffix, straight from Claude Code (`claude-cli/2.1.112`):**

| Where `[1m]` was put | Model on the wire | `context-1m-2025-08-07` beta |
|---|---|---|
| `ANTHROPIC_DEFAULT_OPUS_MODEL` only, `--model` plain | `openrouter/glm-5.2` | no |
| the var **and** `--model` | `openrouter/glm-5.2` | yes |
| the var, `--model opus` (alias) | `openrouter/glm-5.2` | yes |

So the marker never reaches a provider — Claude Code strips it — and the window follows the string the session *selects*, not merely a slot's value.

**Effort, end to end** — the same `claude` through the real bundled Bifrost (config generated by `buildSidecarConfig`, provider base URL pointed at the sink):

| `--effort` | What the provider received |
|---|---|
| medium | `reasoning: { effort: "medium" }` |
| high | `reasoning: { effort: "high" }` |
| max | `reasoning: { effort: "high" }` |

Claude Code sends `output_config: { effort }` plus `thinking: { type: "adaptive" }` under the `effort-2025-11-24` beta; Bifrost converts it to its unified reasoning parameter and out again. Effort therefore needs no mapping from dev3. The `max → high` flattening is Bifrost's own [issue #4320](https://github.com/maximhq/bifrost/issues/4320), not ours.

## Decision

`CatalogModel.extendedContext?: boolean` records whether a model serves a 1M window; absent means "decide from the model id" (`hasMillionTokenWindow`, a family match over the four ids verified today). Existing catalogs therefore get the right answer with no migration, and the checkbox in the API-models table lets the user contradict the guess either way.

`claudePlan` appends `[1m]` to the opus and sonnet slot values — the two aliases whose docs describe the suffix — and to the launch `--model`, which the table above proves accepts it. Fable and haiku keep the plain name rather than an undocumented guess; background work does not need the window. `nativeModelIdForWireName` strips the suffix so a session reporting `openrouter/glm-5.2[1m]` still prices.

## Risks

`[1m]` reaches the shell inside `--model`; `quoteIfUnsafe` already quotes brackets, so zsh cannot glob-expand it. Should Claude Code ever stop stripping the marker, the proxy would be asked for a model name no provider knows and the launch would fail loudly rather than quietly — the wire test above is the only thing standing behind that, and it holds for one CLI version.

The id guess is a family match: a future `glm-5.2` variant with a smaller window would inherit the wrong answer until the user unticks the box.

## Alternatives considered

- **Read the window from the provider's listing.** The sidecar's listing RPC returns ids only (`{ models: string[] }`); carrying capabilities through it is a larger change than this earns.
- **Hardcode the four recommended models with no user-facing field.** Rejected: a user's own 1M model would silently stay on 200k, with no way to say otherwise.
- **Suffix every slot.** Rejected: only opus and sonnet are documented, and an unstripped suffix on a background slot would fail mid-session — exactly the failure mode this feature keeps trying to produce.
