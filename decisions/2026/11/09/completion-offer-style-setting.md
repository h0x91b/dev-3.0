# Completion asks: a dialog by default, a bar in the agent's pane on request

## Context

`completion-offers-render-inline-not-modal` (#2215) moved merge and agent completion asks from the modal to a card at the top-right of the task's terminal, and `revert-inline-completion-offers-to-modal` (#2256) took it back out: the objection was the card's placement. The maintainer then asked for both styles behind a setting. Every open task holds an agent, a tmux session and memory, so the default must be the style that gets an answer soonest, and the inline style must sit where the eye already is: the agent's prompt at the bottom.

## Investigation

On a 145×38 Claude Code pane, a footprint of 80 columns × 6 rows covered 13% text at the top-right (stale output), 29% directly above the input box (the agent's own completion summary), 39% at the bottom-left and 48% at the bottom edge (the input box). A two-row bar at the bottom edge covered only the right end of the status and hint rows. QA then found three more limits: on a split task the terminal's corner is over the shell pane, a 52 px bar clips the input box's bottom border (the third row up in Claude Code's default layout), and a bar whose centred buttons move when its note opens loses the click aimed at Complete.

## Decision

A global setting `completionOfferStyle` (`"dialog"` default, `"inline"`) picks the surface. `src/mainview/completion-offers.ts` holds the pending merge and agent offers and the style, and every surface reads both live. A switch to Dialog applies to new offers only: offers already waiting stay on their task (`staysOnTask`), because opening one modal per waiting ask left the user only two ways out, answering each or refusing each agent with Esc. A switch to On the task closes any open modal, and its offer moves to the bar. On the task, "Keep open" settles every offer on the task (`keepTaskOpen`), so declining the agent never swaps the merge bar in under the pointer. The bar announces itself through a polite live region; it never takes focus. In dialog mode `CompletionOfferDialogHost` asks each offer through `confirm()` with the dialogs that existed before the setting: `buildMergeCompletionDialogOptions` for a merge, the `app.agentCompletion*` copy for an agent, the caller's task card (`dialogInfo`) and folder wording (`keepsFolder`). Each dialog answers only its own offer. The offer stays in the store, so an answer from any client closes the modal. As before the setting, Dialog raises no bell, no toast and no card or sidebar marker, and does not replay merge offers. The new copy and the `getUnsavedWork` check belong to the bar. In inline mode `TaskCompletionStrip` is a 36 px bar at the bottom-right of the agent's pane (`agentPanePlacement`: the pane `TaskPaneState.agentPaneId` names, so a swap never moves the bar onto a shell; the whole terminal for one pane, the agent zoomed, or an unknown pane; when another pane is zoomed over the agent or it sits in another tmux window, the bar spans the terminal and an agent offer gains Show agent, the `reveal` pane action, with a toast if it fails; `agentPaneId` and `reveal` come from the backend in #2325, and until it reports `agentPaneId` the bar frames the first pane by index), capped within 72rem of the pane's left edge; its note and git warning open upward on hover or focus while the title and buttons stay on the bottom line, and a warning that holds a click back stays open. On the task, `CompletionOfferMark` marks the card and sidebar row, a bell and a toast reach a user who looks elsewhere, and merge offers replay after a reload or an app restart through `listPendingMergeOffers`, which reads the persisted, undismissed prompt: the poller's in-memory reservation is cleared by any lifecycle move and by a restart. An agent's request for a task outside the active columns (To Do: another task can ask for it) asks in the dialog in both styles: opening that task shows `TaskDetailModal`, which has no bar, so on the task it would wait unseen with only a card marker. The server sets `noTaskView` on the request when it is made, and `offerAsksInDialog` checks that flag before the style. Such a request raises no bell or toast, like any dialog ask. An agent's request whose attached repo lies in the task's own folder carries `attachedWorktree` (#2299): the dialog and the bar run `getUnsavedWork` bound to that repo, show `task.attachedWorktreeNote`, and report the repo back through `onChecked` only after the check succeeded, so `respondToAgentCompletionRequest` approves removing exactly the checked repo, or none. The user's own Complete/Cancel is not an offer: it asks beside the clicked button or in the modal (`user-completion-confirm-anchored-not-modal`).

## Risks

The dialog interrupts at detection time; users who prefer that it does not pick "On the task". No dialog is asked before the host's settings load, so a stored "On the task" never flashes a modal. An ask on the task can wait longer than an agent's own shell timeout: opencode gives up on `dev3 task move` after 120 s and runs it again. The retried request replaces the first, and an answer then still completes the task (checked live).

## Alternatives considered

- Pinning the bar above the input box: the box sits 3 to 8 rows from the bottom depending on harness and status line, and the rows above it are the agent's summary.
- The #2215 card at the top-right: rejected by the maintainer on the live build.
- A full-size card at the bottom: it covers the input box.
- The bar in `TaskDetailModal` for a To Do task's request: it shows only after the user opens that card, and nothing on the board says to open it except a small marker.
