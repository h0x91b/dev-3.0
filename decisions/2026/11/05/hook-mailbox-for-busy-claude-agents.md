# Busy Claude agents take held messages through their PostToolUse hook

## Context
A `dev3 message` is held until its pane has been quiet for 15 s, then typed (`src/bun/agent-message-hold.ts`). A Claude agent that is mid-turn makes the pane look busy, and Claude Code only reads typed text that arrives mid-turn at its next tool boundary. So a busy receiver paid the 15 s window plus up to one more tool call. Long bodies became a file pointer that cost the receiver an extra Read. dev3 already runs a hook on every Claude tool call to move the status. Claude Code accepts `hookSpecificOutput.additionalContext` from PostToolUse and shows it next to the tool result, capped at 10 000 characters per field (current hooks docs).

## Investigation
Measured on an isolated instance (own `HOME`, `DEV3_HOME`, tmux socket and port), a Claude receiver making ten `sleep 20` calls, sender messages of 146 and 5 044 bytes. Typed path: seen by the model 41.7 s and 25.4 s after the send, plus one Read before the long body was in context (28.1 s). Hook path, same setup: 14.6 s and 16.8 s, body inline, zero extra Reads, each message seen once and nothing typed into the pane. One run each, so the numbers carry the luck of where a send lands in a 20 s tool call: the typed path waits 15 s plus the time to the next tool boundary, the hook path only the latter. The hook itself costs the same as before, a median of 93 ms for the old command and 93-94 ms for the new one (30 calls each, alternated).

## Decision
Claude's PostToolUse now runs `dev3 hook claude-post-tool` (`src/cli/commands/claude-post-tool.ts`). It sends one socket request, `task.claudePostToolUse` (`src/bun/cli-socket/hook-mailbox-commands.ts`), which makes the same guarded status move through the `task.move` handler and then calls `claimHeldAgentMessagesForHook` for the pane. The claim takes leading held messages that opted in, up to `AGENT_MESSAGE_HOOK_MAX_CHARS` (9 000), synchronously, so the claim and the release can never both deliver one message. With nothing held anywhere the drain costs no task lookup. Only agent-to-agent messages on the tmux backend opt in (`scheduled-message-scheduler.ts` `hookText`); a spilled body is read back and sent inline when the envelope fits the cap. A subagent or teammate call (`agent_id` in the payload) and a `claude -p` run in the pane send no pane id and drain nothing. A drain is two-phase: the reply carries a `claimId`, and the adapter acknowledges it (`task.claudePostToolUseAck`, `acknowledgeHookClaim`) only after its stdout write completes. Without an ack within `AGENT_MESSAGE_HOOK_ACK_TIMEOUT_MS` (45 s) the messages go back in front of the pane's hold, so a hook killed mid-turn or a timed-out socket costs a duplicate, never a silent loss. Only the ack writes a receipt (`receiptFor`, `src/shared/agent-message-log.ts` `AgentMessageLogReceipt`) into the same day-file; `readAgentMessageLog` collects each day's receipts before its rows (a receipt can land before its row, which is logged only after the delivery returns) and folds it into the message's own row as `delivered`, `deliveredVia: "hook"`. The receipt has no recipient, seq or body, so the row parser every older version ships rejects it and an older reader lists nothing extra. The settings run `dev3 hook claude-post-tool || <plain move>`: the adapter exits 0 on every runtime failure, so the plain move runs only when the installed `~/.dev3.0/bin/dev3` predates the subcommand. The adapter waits on the same default socket timeout as the plain move, and the settings entry has no hook timeout, as before. Windows has no tmux and no shell for `||`, so its PostToolUse stays the plain move.

## Risks
Hook context reads with more authority than typed text, so external senders and sourceless messages stay on the typed path. A drained message is not typed, and `additionalContext` never shows in the pane, so the adapter also answers `systemMessage` with one line per message (`dev3 message from #<seq>: <subject>`); Claude Code 2.1.318 renders it as `PostToolUse:Bash says: ...` and does not send it to the model. A move failure inside the adapter goes to stderr with exit 0, where the plain move exited non-zero and Claude showed a hook error. Idle agents make no tool calls and keep the 15 s typed delivery.

## Alternatives considered
A second PostToolUse entry for the drain: one more process per tool call. Draining on Stop or UserPromptSubmit: a Stop block interacts with the review move, and mail attached to the user's own prompt changes what the user sent; each needs its own decision. A durable on-disk mailbox: new state under `~/.dev3.0` for a loss case the logs never showed. Native backend: its held writes are forwarded across processes by closure, so it keeps the typed path for now.
