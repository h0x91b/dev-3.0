# ⌘1–9 slot pins sit over the default order

## Context
⌘1–9, ⇧⌘1–9, the remote `G` then N chord and every ⌘N badge walk one list (`digitTargets` in `src/mainview/utils/digitOrder.ts`). It was always derived: the first nine projects in board order, or with "Number keys follow spaces" the first nine mixed entries. Users could not tell why a digit opened what it did and had no direct way to choose it. On 2026-11-09 per-key pinning was rejected; the user has since asked for exactly that.

## Decision
`SpacesFile.digitSlots` (spaces.json, additive optional field) stores up to nine pins, index = digit − 1, each a space or project id or null. `digitTargets` resolves pins first against `digitPinPool` (every space with a live member, every non-Operations project), then fills the unpinned slots from the default order (`digitCandidates`: the dashboard order, see `decisions/2026/11/22/digits-follow-dashboard-order.md`), skipping anything pinned. Pins are **mode-independent**: the setting only decides what the default order is, so a space can be pinned with the setting off and a member project with it on. A pin that no longer resolves behaves as unpinned and is dropped on the next renderer write; the host also unpins a removed project (`unpinRemovedProject`, called by the `removeProject` handler) and a soft-deleted space (`softDelete`), because re-adding the same repo revives the same project id and would otherwise silently bring its old pin back. Key labels come from `digitKeyLabel` (`src/mainview/utils/platform.ts`): `⌘N` on macOS, `Ctrl+N` elsewhere, `G N` in a browser tab. The dashboard edits pins in place: each row and space header renders `DigitKeyControl` (`src/mainview/components/DigitKeyControl.tsx`), a ⌘N chip that opens a 3×3 keypad of all nine keys, and a click or the digit pins that entry; a first version with a header button and a nine-dropdown modal read as unobvious and was dropped; writes go through `setDigitSlots` and the same coalescing pending-write store as the mixed order (`src/mainview/mixed-order-store.ts`), so badges and handlers agree while a write is in flight.

## Risks
spaces.json is rewritten by older builds through load/mutate/save of the parsed object, which keeps unknown fields, so an older version leaves the pins intact and just ignores them. A pinned slot past the end of the default list leaves earlier gaps empty (no key opens anything there); that is the honest reading of "key 5 is pinned".

## Alternatives considered
- **Assign by swapping inside the order** (projects.json order or `mixedOrder`): no new field, but choosing ⌘3 silently reorders the dashboard and the default order loses its meaning; the default order is owned by a separate change.
- **Per-row "Assign to ⌘…" menu items**: no single view of all nine keys, and the dashboard row action budget is spent. The chip is the row's existing key label made clickable, so it adds no action, and its keypad is the nine-key view.
- **A header button opening a nine-dropdown modal** (the first cut): the key was edited far from where it is read, nine `Automatic · name` pickers buried the pins, and the button was easy to miss. Below `md` neither version has an entry point; the keys themselves need a keyboard.
- **Separate pin maps per mode**: doubles the state for a setting most users never flip; one map with a mode-dependent fill is simpler to explain.
