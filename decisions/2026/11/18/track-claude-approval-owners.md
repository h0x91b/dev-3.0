# Track Claude approval owners

## Context
The initial background-tool filter prevented unrelated work from clearing a parent's approval, but also ignored the waiting background agent's own completion. Maintainer review of PR #2317 identified that stuck status and the missing offline tolerance around the new PreToolUse command.

## Investigation
Claude includes session_id and agent_id in permission and tool hooks. PermissionRequest lacks tool_use_id, so it cannot unambiguously identify a pending call among parallel tools in the same conversation. The shared installed CLI can predate the task's hook file: an unknown hook exits 2 during socket discovery when the app is offline, and Claude treats that code as a blocking PreToolUse error.

## Decision
ClaudeApprovalState tracks an in-memory set of waiting owners per task, keyed by conversation and optional background agent, and remembers the working or AI review lane to restore. applyClaudeHookStatus serializes owner updates and guarded status moves; only the waiting owner's activity clears its wait, and other waits remain visible. PreToolUse, permission notifications, failed tools, SubagentStop and TeammateIdle report through handleClaudePreTool; successful tools report through handleClaudePostTool without handing background agents the parent's mailbox. New prompts clear their own wait; SessionEnd cleans up SDK sessions even without a pane. Background work reopening a stopped parent restores its review lane after the final worker stops or becomes idle. Stop uses one serialized adapter instead of concurrent shell moves, recording the stopped parent even while a child approval keeps Has Questions visible. Both tool adapters use one parser and ignore malformed payloads. The prompt ledger from `claude-prompt-hook-commands.ts` stays in front: its PreToolUse, PermissionRequest and PostToolUseFailure handlers now move status through applyClaudeHookStatus, and a parent's failed call only ends its own wait (an interrupted call leaves the agent idle).

A background agent's stop event can be lost (an interrupt, a TeammateIdle without agent_id), and nothing else would ever let the stopped parent's card leave Agent is Working. Each background owner therefore records when it was last heard from; once the parent has stopped and no one is waiting, `scheduleClaudeBackgroundExpiry` (`claude-hook-status.ts`) arms one timer per task, and an owner silent for `CLAUDE_BACKGROUND_STALE_MS` (5 minutes) is dropped, so the card reaches the stopped lane. Waiting owners never expire. An expiry that cannot resolve or move its task (deleted task or project) drops the task's state instead of re-arming, so it can never spin. Task teardown (`clearTaskRuntime`) forgets the task's owners and timer, and `agent.exited` ends the exited session's owners, so a crashed session without SessionEnd cannot pin the next one in Has Questions.

## Risks
Ownership is per agent, not per tool: a parallel sibling tool in the same parent can still clear its wait, explicitly covered by a regression test. TeammateIdle without the optional agent_id cannot be correlated safely and is ignored; the stale timer bounds the result to five minutes in Agent is Working. A background agent that legitimately runs one tool for longer than five minutes after its parent stopped shows Review until its PostToolUse reopens the card. A parent that exits while its own permission prompt is open leaves the card in Has Questions: SessionEnd from the pane only clears the state, and `agent.exited` only moves an in-progress card. State is local to the running app, so after a restart background work conservatively leaves an unowned Has Questions card alone. POSIX commands tolerate only exit 2 with a shell guard; Windows requests the existing --tolerate-app-offline flag because its hook runner has no POSIX shell. An older Windows CLI that predates that flag cannot provide the same guarantee; an app/CLI version mismatch may still lose status reporting until the installed CLI is updated.

## Alternatives considered
Ignoring all background tool hooks loses both their approval resumes and their activity after the parent stops. A single task-wide background-wait flag lets one background agent clear another's question. Terminal-text matching and persistent approval state add complexity without supplying the missing stable tool identity. Dropping every background owner at the parent's Stop fixes a lost stop event too, but flips a genuinely running child to Review until its next tool call, and still strands a card when the lost event comes after the Stop.
